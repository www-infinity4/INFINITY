# Infinity Shared Wallet and Entitlement Contract

## Purpose

Infinity uses one account wallet across every participating repository and application. Repository count is not hard-coded: any present or future Infinity application calls the same entitlement ledger using the authenticated `user_id` and an application `source_key`.

A token can be generated by many activities, but **generation** and **allocation** are separate events. Every generated token remains ledgered even when it is routed to the Infinity system pool rather than the user's spendable wallet.

## Canonical daily rules

| Source | User allocation | Timing | After user limit |
|---|---:|---|---|
| Infinity Mint | 10 x 1-Infinity notes/day | one deliberate mint at a time | mint disabled until next account-day |
| Alien Radio | maximum 10/day | at most 1 qualifying listener token per rolling 60 minutes | no additional user allocation that day |
| Bitcoin Crusher | first 10 qualifying spins/day | immediate | generated spin tokens route to `INFINITY_SYSTEM_POOL` |
| Mario Spin | first 10 qualifying spins/day | immediate | generated spin tokens route to `INFINITY_SYSTEM_POOL` |

These are account-level limits, not browser-local counters. Opening another repository, tab, device, or site cannot reset the allowance.

## Token denomination versus research score

Each user-allocated economy token has a canonical denomination of **1 Infinity unit** inside the Infinity application ledger. Research score, development score, physical-asset state, merchant value observations, or other analytics are stored separately and never silently change the token denomination.

```text
canonical_token
  token_id
  denomination = 1 Infinity
  generated_by
  generated_at
  allocated_to = USER | INFINITY_SYSTEM_POOL

analytics
  research_score
  development_score
  interaction_score
  market_observations
```

## One wallet, many applications

Every application uses the same service contract:

```text
POST /v1/actions/qualify
  user_id
  source_key
  action_key
  occurred_at
  source_token_id?
  optional_input?

RESPONSE
  event_id
  token_id
  denomination
  allocation
  user_daily_count
  user_daily_limit
  next_eligible_at?
```

`source_key` examples:

- `INFINITY_MINT`
- `ALIEN_RADIO`
- `BITCOIN_CRUSHER`
- `MARIO_SPIN`

The server is authoritative. Front ends may optimistically animate a result but must reconcile it against the shared ledger response.

## Bitcoin Crusher interaction rule

A spin must remain fast. User research input is **optional**.

### Quick spin

The user presses Spin. The system immediately creates the spin/action record, checks entitlement, selects a novel research seed automatically, and starts the research job.

### Directed spin

If the user wants to steer it, they may add keywords, a question, a token, a URL, or text. Directed input augments the novelty engine; it is not required before Spin works.

The interface should therefore make the main Spin button primary and place `Add research direction` behind an optional expandable control.

## Generated token allocation

All qualifying actions create a generation record:

```text
TOKEN_GENERATED
  event_hash
  source
  user
  ordinal_for_source_day
```

Allocation is then deterministic:

```text
if ordinal <= source.user_limit:
    allocation = USER
else:
    allocation = INFINITY_SYSTEM_POOL
```

This preserves the information created by later Crusher/Mario spins without falsely crediting unlimited spendable tokens to the user.

## Alien Radio hourly qualification

A listener token requires a qualifying listening event and cannot be allocated more frequently than once per rolling 60-minute interval. The daily user ceiling remains 10. The ledger records play/session evidence separately from the token so refreshing or replaying cannot create duplicate entitlement.

## Infinity Mint

Mint is stricter than the other sources:

- exactly one note is finalized per deliberate mint action;
- no batch `mint 10` action;
- maximum 10 successful note allocations per account-day;
- note serial derives from the canonical token/commit identity;
- attached media, signature, Living Token research, and viewer rendering do not create extra Mint allowance.

## System pool

`INFINITY_SYSTEM_POOL` is a ledger owner, not a deletion bucket. Later-spin tokens preserve their source/action/research provenance and may be used by system features under explicit policy. Moving a token from the pool must itself be ledgered.

## Cross-repository synchronization

Participating repos should not maintain independent balances. They receive a minimal adapter configuration:

```json
{
  "wallet_protocol": "infinity-wallet-v1",
  "ledger_authority": "INFINITY",
  "source_key": "BITCOIN_CRUSHER",
  "local_balance_authoritative": false
}
```

Local storage may cache UI state offline, but balances and allowance counters reconcile from the central ledger.

## Safety and integrity invariants

1. Idempotency key prevents double-credit on retries.
2. Account-day is calculated server-side in a documented timezone policy.
3. Rolling-hour Radio eligibility uses server timestamps.
4. Every generation and allocation is append-only.
5. Research/market scores cannot mutate denomination.
6. UI cannot award itself a token.
7. Later generated tokens are not discarded when the user allocation limit is reached.
8. Repository creation automatically becomes eligible for wallet integration through the shared adapter rather than creating another wallet.
