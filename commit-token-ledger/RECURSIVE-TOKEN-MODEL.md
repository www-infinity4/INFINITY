# Recursive Commit Tokens and Research Enrichment

## Core rule

Every Git commit observed anywhere in the configured GitHub account is ledgered. No commit is discarded merely because it was produced by the ledger, watcher, classifier, documentation system, or an AI research process.

A recursive commit is still useful provenance. The system records it as a derived event and links it to the token or operation that caused it.

## Token identity versus token knowledge

The immutable identity of a token is derived from:

`owner/repository@full-commit-sha`

Everything else is enrichment layered around that identity. A token may accumulate new classifications, project relationships, research notes, citations, summaries, and later interpretations without changing its identity.

## Lifecycle

1. A commit appears in any repository owned by the watched account.
2. The watcher creates or confirms the commit token.
3. The token receives an initial semantic category.
4. The commit is compared with its parent commit(s) to determine what changed.
5. The repository and nearby history are examined to identify why the change appears to have happened.
6. Project lineage is inferred: continuation, repair, fork/reuse, repurposing, documentation, research expansion, or system-generated derivative.
7. A research-writer record is attached to the token.
8. Later evidence may add new notes or reclassify the token without replacing it.
9. If that enrichment itself creates a Git commit, that commit receives its own token and a `DERIVED_RECURSIVE` relationship back to its source.

## Recursive tokens

Recursive tokens are not errors. They are second-order artifacts that document the system documenting itself.

Recommended relationship types:

- `PARENT_COMMIT` — normal Git ancestry.
- `CONTINUES_PROJECT` — expands the same project direction.
- `REPURPOSES_PROJECT` — uses an older repository or component for a materially new purpose.
- `DERIVED_RECURSIVE` — generated by ledgering, enrichment, indexing, or research automation.
- `DOCUMENTS_TOKEN` — commit primarily documents another token.
- `IMPLEMENTS_TOKEN` — commit implements a concept previously represented by another token.
- `RECLASSIFIES_TOKEN` — commit changes taxonomy or metadata associated with an earlier token.
- `FORKS_IDEA` — reuses a concept while moving into a distinct subsystem.

## The “sapphire” pattern

A useful existing component can be treated as a reusable project asset. The ledger does not need to assert that a literal physical resource was discovered. Instead it can record the concrete software/research event:

> An older project contained an artifact, technique, data structure, design, or research concept that was reused as an input to a new project.

That relationship can be represented as `REPURPOSES_PROJECT` or `FORKS_IDEA`, with source and destination tokens linked in the database.

## AI research writer

The research writer should never rewrite Git history. It adds an append-only annotation containing:

- factual commit metadata;
- files changed and diff statistics when available;
- concise description of what changed;
- likely purpose, marked as inference when not explicit;
- repository state before and after the commit;
- project lineage and reused concepts;
- semantic categories and keywords;
- people/bots credited by the Git metadata;
- related commits and tokens;
- external sources when research is performed;
- confidence score;
- provenance for every generated assertion.

## Evidence levels

- `OBSERVED`: directly obtained from Git/GitHub metadata or file content.
- `INFERRED`: interpretation produced from observed evidence.
- `EXTERNALLY_VERIFIED`: supported by an identified outside source.
- `USER_DEFINED`: taxonomy, theory, project meaning, or relationship supplied by the project owner.

This keeps the ledger broad enough for Infinity research while preserving the difference between recorded Git facts and later interpretation.
